# 30 Jul 2026

Signal system refactoring and new Shopify tracking features.

## Projects

### behavora

- Migrated from `data_type` column to `condition_type` on the features model — scoring rules now use a dedicated type system instead of repurposing the data type field.
- Added signal usage tracking: signals now track which scores reference them, enabling better management and visibility into signal dependencies.
- Implemented wishlist tracking in `banner.js` for the Shopify extension — captures wishlist interactions as journey events.
- Refactored `add_to_cart_count` computation to use action-based tracking instead of event counting, with corresponding tests.
- Refactored `eventsPerMinute` method to exclude passive system events (like `mouse_active` and `tab_active`) for more accurate session engagement metrics.
- Added `mouse_active` property to `TrackVisitorPayload` and updated request/service classes and Swagger docs.
- Enhanced `tabActive` signal method to determine visibility based on specific journey actions `tab_visible` / `tab_hidden`.
- Updated feature names and descriptions for `mouse_active` and `tab_active` signals.
- Added backend integration tests for `banner.js` tracking actions.
- Expanded Shopify `PRICE_SORT_INDICATORS` with additional sorting parameters.
- Enhanced `checkoutStarted` detection to include action and additional URL patterns.
- Removed duplicate `is_returning` signal.
- Extracted 9 URL constants in `FeatureCalculator` (CART, CHECKOUT, DELIVERY, RETURN, PRICE_SORT, PRICING, DEMO, CASE_STUDY, BLOG) and extended URL patterns.

## Lessons

The `data_type` → `condition_type` migration is a good example of why domain-specific enums are better than repurposed generic ones. When the condition evaluation logic needs different behavior based on type, having a dedicated column with clear semantics prevents accidental coupling between data storage and business logic.
